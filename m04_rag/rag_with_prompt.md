对,完全正确。**RAG 本质上就是一种构造 prompt 的策略**——它的"输出"就是一个精心拼装好的 prompt,然后再喂给大模型。

## RAG 的 prompt 长什么样

典型的 RAG prompt 结构大致是这样:

```
你是一个客服助手,请基于以下参考资料回答用户问题。
如果资料中没有相关信息,请如实说明。

【参考资料】
片段1:公司差旅报销标准为...
片段2:出差需提前3天提交申请...
片段3:餐饮费用每日上限为...

【用户问题】
出差吃饭一天能报多少?

【回答】
```

可以看到,检索出来的内容只是被**拼接到了 prompt 模板里的某个位置**,其他部分(角色设定、指令、问题、格式要求)都还是常规的 prompt 工程。

## 所以 RAG 工程师其实在做两件事

一是**检索这一侧**:怎么把知识库切片(chunking)、用什么 embedding 模型、怎么排序召回的结果、要不要重排(rerank)等等。

二是**prompt 这一侧**:检索到的内容怎么组织、放在系统提示里还是用户提示里、用什么分隔符、怎么引导模型在资料不足时不胡编、要不要让模型给出引用来源等等。

第二部分就是纯粹的 prompt 工程,和 zero-shot/few-shot 完全是一套技能。事实上,RAG prompt 里**也经常嵌入 few-shot 示例**,告诉模型"当资料里有答案时这样回复,当资料里没有时那样回复"。

## 一个简洁的心智模型

可以这样理解:

- **普通调用**:`prompt = 用户问题 + 指令`
- **Few-shot**:`prompt = 用户问题 + 指令 + 示例`
- **RAG**:`prompt = 用户问题 + 指令 + 检索到的资料`
- **RAG + Few-shot**:`prompt = 用户问题 + 指令 + 检索到的资料 + 示例`

所有这些方法,最终交给大模型的都是**一段文本(prompt)**。模型本身并不知道你是"RAG 系统"还是"普通调用"——它只看到一段输入文本,然后生成输出。RAG 的"魔法"全部发生在**把那段文本拼起来之前**。
